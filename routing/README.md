# 보행 네트워크 (OSM) — 경로탐색 데이터

작성일 2026-09-01 · 산출물: 팀원 핸드오프 `hanwha-routing-handoff-20260901-175810` 를 저장소에 편입한 것
방어 배점: 현업 적용 가능성 20점(실제 걷는 길 위에서 안내한다) · 문제 해결력 15점(도달 경로를 실측 도로망으로)

## 무엇인가

CCTV 23대를 모두 감싸는 범위(+900m)의 **보행 가능 도로망**이다. OpenStreetMap 을 OSMnx 로 받아
`walk` 네트워크로 뽑았다. 대시보드(`docs/index.html`)의 **혼잡 회피 보행 경로**가 이걸 쓰고, 경로 비용에 들어가는 혼잡위험은 `docs/app/field.js` 의 혼잡장에서 읽는다.

| 파일 | 내용 |
| :-- | :-- |
| `download_walk_network.py` | 재생성 스크립트 (핸드오프 원본 그대로, 수정 없음) |
| `requirements.txt` | 재생성에만 필요한 의존성. 평소 실행에는 필요 없다 |
| `../docs/data/routing/walk_graph.json` | 산출물. 노드 9,219 · 간선 26,042 · 총 연장 1,486km(방향별) · 원본 5.95MB(gzip 전송 시 775KB) |

## 재생성

```bash
.venv/bin/pip install -r routing/requirements.txt   # osmnx·geopandas — 무겁다
.venv/bin/python routing/download_walk_network.py
```

Overpass API 를 때리므로 몇 분 걸리고 네트워크가 필요하다. `routing/cache/` 와 `data/pedestrian/` 는
중간 산출물이라 git 에서 제외한다(`.gitignore`). 스크립트는 `docs/data/cams.json` 의 카메라 좌표로
bbox 를 잡으므로, **카메라 목록이 바뀌면 다시 돌려야 한다.**

## 핸드오프에 없던 파일 3종과 처리

스크립트는 산출물 5개를 쓰지만 핸드오프에는 `walk_graph.json` 하나만 있었다.

| 없던 파일 | 처리 |
| :-- | :-- |
| `walk_network.geojson` | **파일로 싣지 않는다.** 원래 `index.html` 이 지도 로드 시 이걸 바로 받는데(eager), 같은 지오메트리가 `walk_graph.json` 에 이미 들어 있어 **모든 방문자가 5MB를 두 번 받는 꼴**이 된다. 경로 계산으로 그래프를 받은 뒤 브라우저가 표시용 GeoJSON 을 만들도록 바꿨다(`walkLayerSync()`). 추가 전송량 0 |
| `walk_graph_stats.json` | 어디서도 읽지 않는 참고용이라 생략. 필요하면 재생성으로 나온다 |
| `yeouido_walk.graphml` · `.gpkg` | GIS 도구용 중간 산출물. `data/pedestrian/` 이라 원래도 git 제외 대상 |

## 핸드오프 원본에서 벗어난 것 — 이탈 1건 (**미결**, 2026-09-02)

**도보 소요 시간 계산.** 원본은 `거리 ÷ 75m/분` 고정 상수였다. 편입하면서 보고서 §3.2 의
밀도별 보행속도(Weidmann Kladek 식, `kladek()`)를 쓰는 `walkMinutes()` 로 바꿨다 —
같은 1.82km 가 **24분 → 47분**이 된다. 인파 속도를 반영하니 값은 커지지만,
"화면의 모든 시간 수치가 같은 속도 모델을 쓴다"는 일관성을 택한 것이다.

**아직 승인·기각이 나지 않았다.** 되돌리려면 `docs/index.html` 의 `walkMinutes(out.meters)` 를
`out.meters/75` 로 바꾸면 된다(1줄). 화면에는 `§3.2 밀도별 보행속도`라고 근거를 붙여 표시한다.

## 알아둘 것

- `walk_graph.json` 은 **경로 찾기를 누를 때만** 받는다(lazy). 첫 지도 클릭 시 미리 받기를 시작한다.
- 브라우저 비용 측정(맥 데스크톱, Node/V8): JSON 파싱 22ms · 그래프 구성 17ms · A* 5ms. 모바일은 몇 배로 보면 된다.
- 경로 탐색은 2단계다. ① 보행로·횡단보도만(`routeStrict`) 쓰는 연결 성분에서 찾고 ② 실패하면 OSM 보행 가능망 전체로 넓힌다. 화면 상태줄에 어느 쪽인지 표시된다.
- ~~비용은 `거리 × (1 + 1.25 × 혼잡위험)` 이다. **가중치 1.25 는 지금도 쓰이는 값**이고 핸드오프 작성자의 추정치다.~~
- **(2026-09-04 변경) 비용을 `거리 ÷ 보행속도(밀도)` 로 바꿨다.** 출처 없는 1.25 를 없애고, 최소화 대상을 사람이 신경 쓰는 값(소요 시간)으로 맞췄다. 속도는 Weidmann(1993) Kladek 식(`docs/app/field.js` `walkSpeed`)이고 `src/nowcast.py` `kladek()` 과 같은 값인지 테스트가 대조한다. 밀도는 혼잡장 값을 등급 사다리(여유 1.5 · 주의 3.0 · 경계 4.0 · 심각 5.0명/m²)로 되돌려 얻는다.
  - **주의:** 이 변경만으로 경로가 잘 바뀌지는 않는다. 혼잡장이 커널의 1200m 성분 때문에 매끈해서 어느 경로든 위험이 거의 같고, **균일 배율·균일 감속은 최소경로를 바꾸지 않는다.** 실험(2026-09-04)에서 반경 150m 짜리 봉우리를 놓아야 비로소 돌아갔다. 카메라 23대가 3km 에 흩어진 지금 관측 밀도로는 그런 봉우리가 안 만들어진다. 결함 대장 M14.
  - **(같은 날 낮 정정) 밀도는 확신도 혼합 ρ_eff 를 쓴다** — 본 곳은 관측 밀도, 못 본 곳은 가로 기본 1.5명/m²(**2026-09-05 정정: 0.8명/m², 여유 등급도 1.5 → 0.5** — `field.js` 주석), 장의 σ 에서 얻은 확신도로 섞는다(`field.js` `blendSeconds`). 위 "봉우리가 안 만들어진다"는 절반이 진단 오류였다: 봉우리가 없는 게 아니라 **사전 수축이 못 본 곳까지 2.25명/m² 로 읽어 봉우리와 배경의 차가 사라진** 것이었다. 혼합 뒤 실측 15대에서 2/6, 축제 배치에서 4/6 목적지가 돈다(신길 +1,278m·22분 단축). 라우터가 고르는 비용과 화면 소요 시간이 같은 식이다.
- **(2026-09-02 정정) 혼잡위험을 만드는 방식은 바뀌었다.** 핸드오프 원본은 관측마다 가우시안을 얹어 더하는 방식(반경 σ=220m, 역시 작성자 추정치)이었는데, 9/1 에 **가우시안 과정 회귀**(`docs/app/field.js`)로 교체했다. 관측 신뢰도를 배제가 아니라 노이즈 σ 로 다루고 불확실성을 같이 내놓기 위해서다. 길이척도는 150m(카메라 화각)·1200m(구역) 두 개이고 **이 값들도 아직 가정**이다 — 9/5 관측이 쌓이면 LOO 교차검증으로 교체한다. σ=220m 는 더 이상 코드에 없다.
- ~~실측 경로가 직선보다 얼마나 도는지: 이벤트광장→여의도역이 직선 1,109m 인데 실제 보행 경로는 **1,820m(1.64배)** 다.~~
- **(2026-09-03 정정) 위 값은 이 저장소의 보행망에서 재현되지 않는다.** 같은 그래프·같은 비용식으로 다시 재면 직선 1,120m 대 경로 **1,471m(1.31배)** 다. `routing_extra` 보완 간선과 태그 필터를 넣고 빼 본 네 조합이 모두 1,471m 였고, 같은 계산이 이벤트광장→마포역 **1,907m**(9/2 `e4b9a1a` 실측)는 정확히 재현한다. 원본 값이 어떤 상태에서 나온 것인지는 확인하지 못했다. 결론이 뒤집히는 정정이라 적어 둔다 — 1.31배는 모델의 `DETOUR = 1.3`(`src/nowcast.py`)과 거의 같으므로, **우회계수를 보정할 근거는 지금 없다.** 재현 절차는 `tools/deck_field_route.mjs` 에 있다(결함 대장 M13).
